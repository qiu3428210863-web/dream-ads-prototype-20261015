# Shader 官网与当前页面的文字锯齿差异

核查日期：2026-10-17。当前项目提交：46c09dd（v1.14.1）。本次仅分析，不修改运行代码。

## 结论

复制相同的曲面公式不等于复制相同的文字渲染。官网先通过 MSDF 字体材质生成可控的字边覆盖率，在 GPU 场景中渲染成纹理，再用浮点坐标执行镜头采样；当前页面把浏览器已栅格化的 DOM 整体交给 SVG 位移滤镜。两者的文字输入、坐标精度与采样控制不同。

上一轮加入的多点重建仍然读取同一张 SourceGraphic，没有升级字形输入，也没有变成官网的 GPU 字体渲染链路。这是优化后仍能看到锯齿的结构性原因；不能把“增加采样分支”称为已经实现官网级文字质量。

主包 SHA-256：`087ed488b7f74a5434cecba3013ca40209b32e53a88ef5c21e229eba6e5d64be`。公开源码快照和哈希记录保存在本地忽略目录 `.tools/shader-audit/`，不把官网整包代码并入本项目。

### 1. 文字确实使用 MSDF，不是猜测

字体 JSON 明确标记 `fieldType: msdf`、`distanceRange: 4`；图集大小为 512×512，字号生成参数为 48。常规字体为 STIX Two Text，包含 89 个字形。

主包约字符偏移 524450–526200 的字形材质读取 RGB 三通道，计算三者中位数，再结合 distanceRange 得到有符号距离；用 UV 的 `fwidth` 确定当前像素的过渡宽度，通过 `smoothstep` 生成边缘透明度，并有约 `1/1.3` 的透明度幂次调整。裁剪边缘也使用导数与平滑过渡。

这些步骤在生成源场景纹理时完成，不是曲面变形之后重新从字形轮廓绘制文字，也不是宣称 MSDF 在所有情况下都比浏览器原生文字更清晰。重要差异是源字边覆盖率和 GPU 渲染方式可控，不需要把浏览器 DOM 的字体栅格结果作为唯一输入。

About Us 的 Au 组件明确创建独立场景、摄像机和 FBO，并将默认字体集合传入 GPU UI 根节点；oZ/o5 负责加载字体图集及字形度量。对应主包偏移约 548900 和 662650–666650。

MSDF 的原理可交叉核对 [msdfgen 官方说明](https://github.com/Chlumsky/msdfgen) 与 [UIKit 字体文档](https://pmndrs.github.io/uikit/docs/tutorials/custom-fonts)。

### 2. 官网没有靠简单开启硬件抗锯齿解决

主包约偏移 1273400 的实际入口配置为 `dpr: [1,1.5]`，WebGPURenderer 的 `antialias` 为 false。支持时使用 WebGPU，否则启用 WebGL 后端。

因此，不能把官网的清晰度归因于 antialias:true、极高 DPR 或未经定位的 FXAA/SMAA。主包内包含大量依赖库代码，本报告只将实际入口与调用链视为证据。

FBO 工具 nv 默认按视口尺寸乘 DPR 分配纹理，放大和缩小过滤均为 LinearFilter；默认颜色纹理可以是 8 位 UnsignedByte，并非每层都使用浮点颜色纹理。这里需要区分“纹理颜色位深”和“镜头采样坐标精度”：官网的镜头坐标在 GPU 节点中计算，不经过当前项目的 8 位 PNG 位移编码。

### 3. About Us 的平滑不能解释为运动模糊

区段配置直接写明：lensDistortion 为 0.16，motionBlur 为 0，bloomIntensity 为 0.1，并有颗粒和色调处理。因此，运动模糊不是 About Us 字体平滑的有效解释。颗粒、色调与轻微辉光可能影响边缘的主观感受，但其贡献没有通过像素对照测量，不能作为主因。

## 当前代码中的限制

### 文字输入仍然是浏览器的栅格结果

`dist/crt.js` 把 main 与 footer 纳入过滤视口。`dist/lens-model.js` 的 pipeline 中，每一路 `feDisplacementMap` 都以 SourceGraphic 为输入。位移后没有字形轮廓、距离场或字边导数可供重建；输入中已损失的细笔画不能靠平均几个采样点恢复。

二点/四点平均属于现有正文图像的空间重建，不等于在更高分辨率重新渲染字形。它可能使边缘柔和，也可能只增加轻微软化，实际效果受浏览器输入图像和插值实现影响。

### 当前抗锯齿增强可能根本没有启用

当前 quality 只在物理视口像素不超过 300 万且内存提示大于 4GB 时启用多点；慢帧机制还会进一步降为单点。

调用当前代码所得示例，内存提示 8GB、8 个逻辑核心：

| CSS 视口 | DPR | 初始采样分支 | 位移图尺寸 | 坐标编码步长，物理像素 |
| --- | --- | --- | --- | --- |
| 1440×900 | 1 | 4 | 360×225 | 约 0.234 |
| 1920×1080 | 1 | 2 | 480×270 | 约 0.309 |
| 1920×1080 | 1.25 | 1 | 482×271 | 约 0.385 |
| 2560×1440 | 1 | 1 | 482×271 | 约 0.411 |

Windows 125% 缩放是一个相关场景：若 CSS 视口为 1920×1080，乘 DPR² 后超过 300 万，会回到单点。这里没有测得用户实际视口或 DPR，所以不能认定这就是用户机器当前选中的档位。

为控制性能而退回单点是上一版策略的质量盲点：高 DPR 不等于源文字经历非线性采样后就不会有可见锯齿。

### 位移坐标仍使用 8 位数据

field 的 Uint8ClampedArray 把横纵偏移编码到 PNG 的 R/G 通道；每个通道只有 256 个级别。表中的编码步长是 `scale / 255 × DPR`。图中数据随后可能经过插值，所以不能把该值直接等同于最终文字台阶的大小，但它确实是额外的控制误差来源。

官网同样可以使用 8 位颜色纹理；不同之处在于镜头坐标不需要先被量化成 PNG 的 R/G 偏移值。

## 为什么前几次修改没有达到目标

提高控制图精度、移除文字额外阴影、改变字体平滑属性，都没有改变 DOM → SourceGraphic 这一关键输入环节。新增多点只是重建同一份图像，而且部分配置会关闭多点。此前的自动检查验证了分支、权重与滚动状态，不能作为字边清晰度已经改善的证据。

## 与官网接近的后续方向

要同时保留明显全局曲面和接近官网的字边，需把可见文字/图形的渲染与镜头合成纳入同一套可控 GPU 管线：MSDF 或等效的字形覆盖率重建、明确的纹理尺寸和过滤方式、浮点镜头坐标，以及逐浏览器的画质与性能对照。不是继续给 SVG 多加几个平均分支。

迁移时仍需保留语义 DOM、键盘、表单、文本选择和无 GPU 时的可读回退。官网当前预生成图集只含 89 个字形，不能原样拿来支持任意中文内容；字体字符覆盖必须另行设计。以上是架构方向，本次没有执行重构。

## 判断边界

本报告确认了公开代码与项目代码的链路差异，没有在相同屏幕、视口和缩放下取得两站的输出像素、实际 GPU 缓冲区尺寸及边缘误差测量。因此能够指出为什么现有方案不能等价复刻官网的画质，也能解释观察到的差异，但不能把 MSDF 或某个单独设置宣称为已实测占比最高的唯一原因。官网也不是数学意义上完全没有锯齿。
